概念地圖：先搞懂這五個東西

這本手冊的指令都用 docker compose（中間是空格）。舊版寫成 docker-compose（中間是橫線），意思一樣，但舊版已經不再更新。

docker-compose.yml＝整個專案的說明書 寫著要開哪些容器、各用哪個 image、要掛哪些 volume。在它所在的資料夾下 docker compose 指令，就會照這份說明書做事。
image（映像檔）
像是「安裝光碟」，只能讀、不能改。
例：mariadb:12.2.2、nginx:1.31.3
冒號後面是版本（tag）。
容器（container）
用 image 裝出來、正在跑的程式。
可以隨時刪掉重建。
容器刪掉，裡面的改動就跟著消失。
volume（資料卷）
像「外接硬碟」，插在容器上。
容器刪掉重建，資料還在。
資料庫的資料都放這裡。
network（網路）
容器之間的內部電話線。
同一個網路裡，用 service 名稱互相連線，例如 db:3306。

我想要⋯

下面的 php、db 等是 docker-compose.yml 裡 services: 底下的名稱（service 名稱），換成你自己的。

啟動、停止容器

docker compose up -d在背景啟動全部容器（-d 是背景執行，終端機可以繼續用）
docker compose up -d db只啟動 db（它依賴的容器會一起起來）
docker compose stop停止容器，容器留著，下次 start 很快
docker compose start把停止的容器再開起來
docker compose restart php重開 php（不會套用新設定，見「讓設定生效」）
docker compose down停止並刪除容器和網路；volume 會留著，資料不會掉
小心 docker compose down -v：加了 -v 會連 volume 一起刪，資料庫資料會全部消失，而且救不回來。

看狀態：哪些在跑、吃多少資源

docker compose ps這個專案有哪些容器在跑、開了哪些 port
docker compose ps -a連已停止的也列出來
docker ps整台機器所有在跑的容器（不分專案）
docker compose ls整台機器有哪些 compose 專案在跑
docker stats --no-stream每個容器的 CPU、記憶體用量（拿掉 --no-stream 會持續更新）
docker compose top每個容器裡跑著哪些程式
docker compose port db 3306查 db 的 3306 被對應到本機哪個 port
狀態欄怎麼看：Up 5 minutes 正常；Restarting 表示一直當掉又重開，要看 log； Exited (0) 是正常結束，Exited (1) 之類非 0 的數字是出錯結束。 (healthy)／(unhealthy) 是健康檢查的結果。

看 log：出錯時第一件事

docker compose logs php看 php 的全部 log
docker compose logs -f php持續跟著看新的 log（Ctrl+c 離開，容器不會停）
docker compose logs -n 50 php只看最後 50 行
docker compose logs --since 10m只看最近 10 分鐘，全部容器一起
docker compose logs -t db每行前面加上時間
docker compose logs db | grep -i error只挑出含 error 的行
log 是空的？有些程式把 log 寫進容器裡的檔案，不是印到畫面上。 這時要進容器看檔案，或看專案有沒有把 log 目錄掛到本機（例如 ./Logs）。

進容器、在容器裡下指令

docker compose exec php sh進到 php 容器裡（有 bash 的話可以把 sh 換成 bash），exit 離開
docker compose exec php composer install不進去，直接在容器裡跑一個指令
docker compose exec -u root php sh用 root 身分進去（要裝東西、改權限時）
docker compose exec -w /var/www php ls指定在哪個資料夾執行
docker compose exec -T db mariadb-dump ... > backup.sql輸出要存成檔案、或在腳本／CI 裡跑時，加 -T
docker compose run --rm php php -v另外開一個臨時容器跑指令，跑完自動刪掉（容器沒在跑也能用）
docker compose cp php:/var/www/a.log ./把容器裡的檔案複製到本機（反過來寫就是複製進去）
exec 和 run 的差別：exec 進到正在跑的那個容器； run 是用同一個 image 另開一個新的。改資料、看現場狀況用 exec。
為什麼要 -T：沒加 -T 時，Docker 會模擬一個互動式終端機， 輸出裡可能混進控制字元，備份檔就壞了。CI 裡沒有終端機，不加也可能直接報錯。

改了設定，讓它生效

改了 docker-compose.yml 或 override 檔docker compose up -d（只會重建設定有變的容器）
改了 Dockerfiledocker compose up -d --build
改了 Dockerfile，但 build 好像沒更新docker compose build --no-cache php，再 up -d
改了 .env 裡的變數docker compose up -d
設定沒變，但想全部重建docker compose up -d --force-recreate
先確認合併後的設定長怎樣docker compose config
最常見的誤會：docker compose restart 不會套用新設定。 它只是把同一個容器停掉再開，設定還是舊的。因為設定只有在「建立容器」的時候才寫進去，所以要用 up -d 讓它重建。
程式碼要不要重建？如果程式碼是用 volumes 掛進容器（例如 ./api:/var/www），存檔就生效，不用重建。 如果是在 Dockerfile 裡用 COPY 複製進去，就要 --build。

image 與版本

docker compose pull下載 compose 檔裡寫的 image（不會重建容器，之後要 up -d）
docker image ls本機有哪些 image
docker compose images這個專案的容器各用哪個 image
docker compose config --imagescompose 檔裡寫了哪些 image
docker compose exec db mariadb --version查容器裡程式的實際版本
docker manifest inspect nginx:1.31.3確認這個版本 tag 在 Docker Hub 上存在（有輸出就是存在）

tag 怎麼寫比較安全

mariadb、mariadb:latest最危險：每個人裝到的版本看下載時間而定
redis:7主版本固定，小版本還是會變
redis:7.4.8-alpine最穩：大家裝到的一模一樣
Dockerfile 的 FROM 也要鎖：docker-compose.yml 鎖好了， 但 Dockerfile 寫 FROM nginx:latest 的話，每個人 build 出來的版本還是不一樣。
資料庫只能升版、不要降版。新版寫過的資料，舊版常常讀不了。鎖版本前先去每台機器查實際版本，見情境「鎖版本前先查各環境」。

資料 volume

docker volume ls列出所有 volume
docker volume inspect 名稱看 volume 的詳細資料，Mountpoint 是它在本機的實際路徑
docker compose config --volumes這個專案用了哪些 volume
docker volume rm 名稱刪掉 volume（容器還在用時會拒絕刪除）

兩種掛法

- db-data:/var/lib/mysqlnamed volume：Docker 自己管，放資料庫這類資料
- ./api:/var/wwwbind mount：直接掛本機資料夾，放程式碼，改了馬上看到
volume 的真實名稱會加上專案名稱：compose 裡寫 db-data， 實際名稱是 專案名稱_db-data。所以專案名稱一改，Docker 會開一個全新的空 volume，見情境「資料庫看起來被清空了」。

網路：容器之間怎麼連

容器連同專案的另一個容器用 service 名稱，例如 db:3306、http://nginx
本機瀏覽器連容器用 ports 開出來的 port，例如 localhost:8080
容器連本機（宿主機）上的服務Linux 要在 service 加 extra_hosts: ["host.docker.internal:host-gateway"]，再連 host.docker.internal
docker network ls列出所有網路
docker network inspect 名稱看有哪些容器接在這個網路上

ports 的寫法

"8080:80"本機 8080 → 容器 80
"127.0.0.1:8080:80"同上，但只有本機自己連得到，別台電腦連不到
"3306"容器的 3306 對應到本機隨機一個 port，用 docker compose port 查
容器裡的 localhost 是容器自己。 在 php 容器裡連 localhost:3306，找的是 php 容器自己，不是資料庫。要連 db:3306。
跨專案互連：在 compose 檔的 networks 設 external: true， 幾個專案接到同一個事先建好的網路（docker network create 名稱），就能用 service 名稱互相找到。

override：每台機器不一樣的設定

docker-compose.yml 旁邊放一個 docker-compose.override.yml， 下 docker compose 指令時會自動讀進來，疊加在主設定上。

單一值：restart、image、commandoverride 的值蓋掉原本的
environment同名變數用 override 的，其他保留
volumes容器內路徑一樣就取代，不一樣就加上去
ports兩邊都保留，不會取代

override 和 docker-compose.dev.yml 這類檔案的差別

docker-compose.override.yml自動讀取；通常不進版控，放單一台機器的個人設定
docker-compose.dev.yml 等要自己用 -f 指定；通常進版控，放某個環境的正式設定
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d
什麼時候不會自動讀 override：用了 -f、設了環境變數 COMPOSE_FILE、或檔名打錯。 檔名錯了不會報錯，只會被靜靜忽略，所以改完一定要跑 docker compose config 確認。
後面的檔案蓋前面的。用 -f 時主設定放第一個，每次都要帶齊，漏帶一個就會用錯設定啟動。

開機自動啟動（restart policy）

restart: "no"（預設）不自動啟動，重開機後要自己 up -d
restart: always當掉就重開；Docker 啟動時（例如重開機）也會跟著啟動
restart: unless-stopped跟 always 一樣，但你手動 stop 過的，重開機後不會自己起來
restart: on-failure只有出錯結束（結束碼不是 0）才重開；正常結束就不管它
docker inspect -f '{{.HostConfig.RestartPolicy.Name}}' 容器名稱查某個容器現在的設定
docker update --restart=no 容器名稱不改檔案，直接改正在跑的容器（下次 up -d 重建時會被 compose 檔蓋回去）
伺服器要、本機不要？主設定不寫 restart，只在伺服器的 override 檔寫。見情境「伺服器要開機自動啟動，本機不要」。

容器名稱怎麼來的

容器專案名稱-service名稱-編號，例如 myapp-db-1
volume專案名稱_volume名稱，例如 myapp_db-data
預設網路專案名稱_default
專案名稱預設是資料夾名稱；可以用最上層的 name:、-p 或 COMPOSE_PROJECT_NAME 改

想改容器名稱

在 service 加 container_name: 新名字只改容器名稱，volume 不受影響，比較安全
改專案名稱容器、volume、網路全部改名；volume 變成新的空 volume
改名前先搜一遍：部署腳本、CI、cron 裡寫死的 docker exec 舊名稱 要一起改，不然會找不到容器。

清空間：磁碟快滿了

docker system df先看空間被誰吃掉（image、容器、volume、build cache）
docker image prune刪掉沒有名字的舊 image（重新 build 後留下的）
docker image prune -a刪掉所有沒有容器在用的 image（之後要用會重新下載）
docker builder prune清 build 快取，通常最佔空間
docker container prune刪掉所有已停止的容器
docker system prune上面幾項一次清（不含有名字的 image 和 volume）
小心 docker volume prune -a：會刪掉所有「目前沒有容器在用」的 volume。 專案剛好 down 著的話，它的資料庫 volume 也會被刪。

全忘光時的救命指令

docker compose --help列出所有子指令
docker compose up --help某個子指令有哪些參數
docker compose config看合併後、變數代換後的完整設定
docker inspect 容器名稱容器的所有細節（環境變數、掛載、網路、restart 設定）
docker events即時看 Docker 正在做什麼（建立、啟動、當掉），Ctrl+c 離開
--dry-run加在 compose 指令後面，只顯示會做什麼、不真的做

使用情境：一步一步照著做

遇到問題時，照順序做。每個情境都先講「為什麼會這樣」，再給步驟。

改了 override，但沒生效

為什麼：設定只在建立容器時寫進去。restart 只是停掉再開同一個容器，所以設定還是舊的。

  1. 確認 Docker 有讀到新設定：
    docker compose config
    看裡面有沒有你改的值。沒有的話，檢查檔名和位置。
  2. 重建有變動的容器：
    docker compose up -d
  3. 確認容器真的換了：docker compose ps 的 Up 時間會變成剛剛。

伺服器要開機自動啟動，本機不要

為什麼：把 restart: always 寫進共用的 docker-compose.yml，每個人的電腦重開機後，這些容器都會自己跑起來。

  1. 共用的 docker-compose.yml 不寫 restart。
  2. 在 repo 的 .gitignore 加一行 docker-compose.override.yml，避免有人不小心 commit。
  3. 只在伺服器建立 docker-compose.override.yml： 
    services:
  php:
    restart: always
  db:
    restart: always
  4. 確認有讀到：
    docker compose config | grep restart
  5. 套用：docker compose up -d

部署時 git pull 失敗

為什麼：有人在伺服器上直接改過 docker-compose.yml，repo 的新版本也改到同一個檔案，git 不知道要留哪個，就拒絕更新。 錯誤訊息通常有 Your local changes ... would be overwritten。

  1. 在伺服器看手動改了什麼：
    git diff docker-compose.yml
  2. 把這些「只有這台機器要」的設定搬到 docker-compose.override.yml（做法見上一個情境）。
  3. 把 docker-compose.yml 還原成 repo 的版本：
    git checkout -- docker-compose.yml
  4. 用 docker compose config 確認合併結果跟原本一樣。
  5. 回 CI 重跑部署。
原則：伺服器上不要直接改進版控的檔案。機器專屬的設定放 override 或 .env。

鎖版本前，先查各環境的實際版本

為什麼：原本寫 latest 時，每台機器下載的時間不同，版本也不同。 如果照你本機的舊版本鎖，版本比較新的機器部署時就會被降版，資料庫可能讀不了資料。

  1. 在每台機器（本機、測試機、正式機）查實際版本： 
    docker compose exec db mariadb --version
docker compose exec redis redis-server --version
docker compose exec mongo mongod --version
  2. 每個服務都取最新的那個版本來鎖。升版可以，降版不行。
  3. 確認這個 tag 存在：
    docker manifest inspect mariadb:12.2.2
  4. 改 compose 檔，例如 image: mariadb:12.2.2。Dockerfile 的 FROM 也一起改。
  5. 版本比較舊的機器要升版，接著做下一個情境。

資料庫升版本

為什麼要多做幾步：升版後，資料庫的系統表要用 mariadb-upgrade 更新。而且容器剛啟動時資料庫還沒準備好，太早下指令會失敗。

  1. 先備份（-T 不能省，不然備份檔會壞）： 
    docker compose exec -T db sh -c 'mariadb-dump -uroot -p"$MYSQL_ROOT_PASSWORD" --all-databases --single-transaction --routines --events' > backup.sql
tail -1 backup.sql
    最後一行是 -- Dump completed ... 才代表備份完整。
  2. 改 compose 檔的版本後，啟動新版：
    docker compose up -d db
  3. 等資料庫準備好：
    docker compose logs db | grep "ready for connections"
    有出現才往下做。
  4. 更新系統表： 
    docker compose exec db sh -c 'mariadb-upgrade -uroot -p"$MYSQL_ROOT_PASSWORD"'
  5. 確認資料還在，例如：SELECT COUNT(*) FROM 某個表。
看到 Can't connect to local server through socket：通常只是太早下指令，資料庫還沒啟動完。等 log 出現 ready for connections 再跑一次。
不想手動跑 mariadb-upgrade：官方 MariaDB image 支援環境變數 MARIADB_AUTO_UPGRADE=1，啟動時會自動做。

容器名稱太長，想改短

為什麼名稱會長：名稱是 專案名稱-service名稱-編號。資料夾叫 myapp、service 又叫 myapp_db，就會變成 myapp-myapp_db-1。

  1. 在每個 service 加 container_name： 
    services:
  myapp_db:
    container_name: myapp_db-1
  2. 搜尋 repo 裡寫死舊名稱的地方（部署腳本、CI、文件），一起改：
    git grep -n "myapp-myapp_"
  3. 重建：docker compose up -d，舊名稱的容器會被換掉。
  4. 確認資料還在。
不要用改專案名稱的方式改名。專案名稱一變，volume 名稱也跟著變，Docker 會開一個新的空 volume，資料庫看起來就像被清空。
程式裡的連線設定不用改：容器之間是用 service 名稱連線（myapp_db），不是容器名稱。

資料庫看起來被清空了

為什麼：最常見的原因是專案名稱變了，例如資料夾改名、移到別的路徑、加了 -p 或 name:。 volume 名稱前面有專案名稱，所以 Docker 以為是新專案，開了一個新的空 volume。舊資料通常還在。

  1. 列出 volume，找舊的那個：
    docker volume ls
    例如同時有 old_db-data 和 new_db-data。
  2. 看容器現在掛的是哪個：
    docker inspect -f '{{range .Mounts}}{{.Name}} {{end}}' 容器名稱
  3. 最簡單的救法：把專案名稱改回原本的，再 docker compose up -d。
  4. 如果要保留新名稱，在 compose 檔裡指定用舊的 volume： 
    volumes:
  db-data:
    name: old_db-data
    external: true
在搞清楚之前，不要執行 docker volume prune 或 down -v。舊資料就在那個沒被使用的 volume 裡。

改了程式碼，但畫面沒變

為什麼：要看程式碼是怎麼進到容器的，不同方式有不同的生效方法。

  1. 看 compose 檔的 volumes 有沒有掛程式碼資料夾（例如 ./api:/var/www）。
  2. 有掛：檔案已經同步了。問題通常在程式自己的快取，例如框架的 config cache、PHP 的 opcache。清掉快取，或 docker compose restart php。
  3. 沒掛（Dockerfile 用 COPY）：要重新 build：
    docker compose up -d --build
  4. 還是沒變：進容器看檔案是不是新的：
    docker compose exec php cat 檔案路徑
前端也一樣：如果網頁讀的是打包好的 dist，改原始碼後要重新 build 前端才會更新。用開發伺服器（例如 Vite）看頁面時，存檔就會即時更新。

容器一直重啟或起不來

為什麼：容器裡的主程式一結束，容器就停了。有 restart: always 時，它會不停重開，狀態顯示 Restarting。

  1. 看狀態和結束碼：
    docker compose ps -a
  2. 看最後的 log，錯誤原因通常在這裡：
    docker compose logs -n 50 服務名稱
  3. 常見原因：
    • 環境變數沒設，例如 .env 少了資料庫密碼。用 docker compose config 看變數有沒有代換成功。
    • 設定檔語法錯，例如 nginx 的 conf。
    • 依賴的服務還沒準備好。見下方說明。
depends_on 只保證「先啟動」，不保證「準備好」。 要等資料庫真的可以連線，依賴的服務要寫 condition: service_healthy，資料庫也要設 healthcheck。 或是啟動時用 docker compose up -d --wait 等全部就緒。

啟動時說 port 被佔用

為什麼：本機已經有別的程式或別的容器用了同一個 port。錯誤訊息是 port is already allocated 或 address already in use。

  1. 找出是誰佔用（把 8080 換成你的 port）： 
    docker ps --filter publish=8080
ss -ltnp | grep :8080
  2. 是別的容器：停掉它，或其中一邊改 port。
  3. 是本機程式（例如本機裝的 MySQL）：停掉它，或把 compose 的 port 改掉，例如 "8081:80"。
每個人想用不同 port：compose 檔寫成 "${WEB_PORT:-8080}:80"，各自在 .env 設 WEB_PORT。沒設時預設用 8080。

容器裡連不到另一個服務

為什麼：最常見的是在容器裡用了 localhost。容器裡的 localhost 是容器自己，不是你的電腦，也不是別的容器。

  1. 連同專案的容器：主機名稱用 service 名稱，例如 db，port 用容器內的 port（3306），不是對外的 port。
  2. 確認兩個容器在同一個網路：
    docker network inspect 網路名稱
  3. 從容器裡直接測試連線：
    docker compose exec php sh -c 'curl -sS -m 5 http://nginx/ -o /dev/null -w "%{http_code}\n"'
    回 200 或其他 HTTP 狀態碼就是連得到；逾時或 Could not resolve host 就是網路不通。
  4. 要連的是區網上別台機器：用它的 IP，並確認那台的防火牆有開。

磁碟滿了（no space left on device）

為什麼：每次 build 都會留下舊 image 和快取，時間久了會吃掉幾十 GB。

  1. 看是誰吃掉空間：
    docker system df
  2. 先清最安全的兩項： 
    docker builder prune
docker image prune
  3. 還不夠，再清沒在用的 image（之後要用會重新下載）：
    docker image prune -a
  4. volume 最後才動，而且要一個一個確認後用 docker volume rm 名稱 刪，不要整批 prune。
